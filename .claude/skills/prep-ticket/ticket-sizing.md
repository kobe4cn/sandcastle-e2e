一次 implement 会话要在 ~150k 上下文内做完；光写代码就要约 100k，所以票必须小，并且要告诉 implementer 在哪里动手。

## 大小上限

- 最多 **3 条验收标准**，新增约 **800 行以内**（含测试）。
- 最多改 **4 个已有文件**（指引里的 `Change` 行；新文件、测试、迁移、文档不算）。三条验收标准也可能散到六个模块，每个已有文件都要先读才能改。
- 超限就拆成更薄的端到端切片：纵向拆，每张子票都能单独演示或测试；不要按层拆（「后端一张、前端一张」）。
- 父票保留原正文，加 `## Split into` 列表、去掉 `ready-for-agent`。每张子票有 `## Parent`、`## Blocked by` 和 `ready-for-agent`。被父票 block 的别的票，改指到对应子票。

## 及时拆

blocker 都做完、轮到它时才拆票、写指引。提前写的指引指向的代码会被后面的票挪走。

指引不能留没定的设计决定（「如果 #95 决定 X，就……」）：准备时就定下来写进指引；需要人定的，按标签规则交给人。

## `## Implementation guide` 的格式

只写结论，不贴代码。

```markdown
## Implementation guide

- **Change**: `path/file.ts:123-180` `functionName`：改什么。一个文件一行，给出要改的函数的行范围，implementer 只读这一段。票要改的每个已有文件都必须出现在 `Change` 行上、路径放在最前面的反引号里：编排脚本靠这些行判断两张票能不能并行，漏写会让并行的两张票改到同一个文件，到合并时才冲突。一批只改一行的文件可以写成 `- **Change**（说明）：`，下面每个文件一条缩进子条目 `` `path:行` ``。
- **New**: `path/new-module.ts`：导出什么。
- **Reuse**: `fnName(arg: Type): Ret`，在 `path:line`；表 `x` 的列 `a, b`。
- **Decisions**: 相关的设计决定记录（只列相关的）。
- **Tests**: 放哪个文件、从哪个接口测、用哪些夹具，以及一个可照着写的已有用例（文件 + 用例名）。
- **Browser check**（只在改页面时）：以什么角色打开哪个页面、做什么、应该看到什么。
- **Watch out**: 不显眼的约束（隐私、权限、迁移）。
```
